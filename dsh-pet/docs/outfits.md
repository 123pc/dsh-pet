# 原生换装

右键桌宠 → 换装。浏览器和桌面使用相同目录、菜单和单次宿主请求，独立侧栏不是依赖。没有安装关联形态时不增加菜单项。

角色包顶层可以声明：

```json
{ "outfit": { "base": "main", "label": "形态名称" } }
```

base 是已经安装的基础配置条目 key，label 是显示名称。只能关联一层；循环、缺失的基础条目或未关联的种类不会混进候选。核心不写死 Claude ID，包作者可以沿用这一机制。

宿主在同组的 pets[].outfits 派生 `{id,label,current}`；这是只读菜单数据，不写回配置。原生菜单调用 `POST /dsh-pet-7340/pet-outfit`，请求 `{id,target}`。成功返回与 GET /config 同形的聚合，业务失败返回 HTTP 200 + `{ok:false,reason,message}`。JSON 错误和方法错误分别是 400/405。

换装切换的是两个已安装实例的可见性，活动实例 ID 会改变。各形态名称、人设、记忆和动作库独立保留；外部控制程序应重新读取配置定位可见实例。没有重写原版资源，也不把一套动作名硬塞进另一套素材。

源实例隐藏，目标继承源显示端。目标已在其它端显示时合并为 both，保留目标尺寸位置；隐藏目标沿用源尺寸和配置初始位置。其它实例不变。这里不承诺复制拖拽后的临时坐标。

该请求与 config/pet-display/pet-config 共用队列：先准备所有文件，再提交；常规写入异常恢复修改前原文，成功后统一发配置变更信号、释放源/目标占用并重载桌面一次。跨文件提交不能视作可抵御进程崩溃或断电的数据库事务。

已有角色不声明 outfit 时沿用原行为。角色素材安装只增加关联元数据；首次升级宿主代码需重载插件本身，单独重载桌面 Helper 不会更新宿主路由。

回归包括旧配置、候选隔离、完整往返、并发保存、已有目标显示端合并、第二层写入失败后的逐字节恢复、HTTP 200 失败处理。上游新结构的菜单接入由自动测试和构建验证，尚未替换现有安装进行实机验收。
